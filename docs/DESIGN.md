# 微信自动回复系统 · 设计文档

> 状态：已评审通过，作为后续开发的基准。
> 讨论定稿日期：2026-09-17

## 1. 目标与范围

对微信中**白名单内的 1 对 1 会话**，自动识别新消息并调用 LLM 生成回复，**完全自动发送**。

第一期范围：

- 只处理**文字消息**；图片 / 语音 / 表情包 / 文件只记日志、不回复；
- 只处理 **1 对 1 会话**，群聊不处理（靠白名单天然排除，不做专门识别）；
- 白名单规模 1~99 人，走配置文件，支持每联系人个性化配置；
- LLM 起步用智谱 GLM，通过 OpenAI 兼容协议接入，后期可切换多家供应商。

## 3. 总体管线

```
主循环（串行，扫描间隔 1~2 秒）
  ├─ ① 捕获微信窗口图像（PrintWindow，窗口被遮挡也有效，见 §3.1）
  ├─ ② 变化检测（pHash）：无变化 → 直接进入下一轮，零成本
  ├─ ③ 红点扫描：扫描会话列表顶部可见行，定位未读徽标
  ├─ ④ 逐个点击红点会话 → OCR 顶栏联系人名 → 白名单模糊匹配
  │      不在白名单（含群聊）→ 忽略
  ├─ ⑤ 消息气泡粗分类：文字 / 图片 / 语音 / 表情包
  │      非文字 → 记日志，不回复
  ├─ ⑥ 裁剪最新文字气泡 → 本地 OCR → 文本（带置信度）
  ├─ ⑦ 安全闸门链（见 §8）→ 任一道不过 → 记日志 + 标记需人工
  ├─ ⑧ LLM 生成回复（文本协议，含该联系人最近 8~10 轮上下文）
  ├─ ⑨ 发送：写剪贴板 → 粘贴 → OCR 验证输入框 → 回车 → 验证输入框已清空
  └─ ⑩ 审计日志落库
```

关键省成本逻辑：LLM 每次只收到纯文本（几百字），不是截图；视觉模型只在 OCR 低置信度时兜底（第一期可不做，留接口）。轮询重活只在画面变化时触发。

### 3.1 窗口捕获方案（后台感知层）

核心原则：**截窗口，不截屏幕**。让微信把自身界面重绘到内存位图，不从屏幕读像素，因此窗口被其他窗口遮挡（甚至完全盖住）不影响捕获。

| 方案 | 定位 | 说明 |
|---|---|---|
| `PrintWindow` + `PW_RENDERFULLCONTENT` | **首选** | Win8.1+ 支持。微信 4.x 是 GPU 合成自绘界面，必须带此标志，否则拿到黑图/残影。该方案存在黑图的可能性，**M1 第一项就是实测验证**；实测失败则启用备选 |
| Windows Graphics Capture (WGC) | 兜底 | Win10 1803+（本机 22H2 满足），系统级窗口捕获，对 DirectX 渲染窗口有官方保证。Python 侧接入较重（winrt 绑定），部分版本会在被捕获窗口周围画黄框 |

**窗口相对坐标红利**：按窗口截图后，所有模板坐标均为窗口相对坐标，与微信窗口摆在屏幕哪个位置无关，比截屏幕方案更稳。

**最小化是硬边界**：最小化的窗口没有渲染表面，PrintWindow / WGC 都拿不到有效内容。运行前提：**微信保持打开状态即可，可以被完全遮挡，但不能最小化、不能关到托盘**。检测到最小化时用 `ShowWindow(SW_SHOWNOACTIVATE)` 自动恢复（显示但不抢焦点）；关到托盘无法自动恢复，靠使用习惯保证。

## 4. 消息获取设计（会话定位）

**不采用"置顶聊天 + 固定坐标"方案**（白名单最多 99 人，置顶不现实）。

利用微信会话列表按最新消息排序的特性：**新消息会把会话顶到列表最上方**，因此：

1. 红点扫描只需要覆盖列表顶部可见的若干行，x 范围固定（头像列），y 从上往下扫；
2. 发现红点 → 点击该会话 → OCR 窗口顶栏联系人名（大字号、干净背景，识别稳定）；
3. 名字与白名单做**模糊匹配**（容忍 OCR 认错 1 个字，编辑距离阈值可配）；
4. 匹配不上 → 不在白名单，直接忽略。群聊因群里任何人名都匹配不上 1 对 1 白名单而被天然排除。

防重复回复：每联系人对"已处理消息"记指纹（气泡区域 hash + OCR 内容 hash 双重），已处理的不重复进 LLM。

## 5. 消息发送设计

- 输入方式：**剪贴板写入 + Ctrl+V 粘贴 + Enter**，不用模拟逐键输入（中文输入法不可靠）；
- 剪贴板读写前后保存并恢复原内容；
- **闭环验证**：粘贴后 OCR 输入框，与预期回复一致才按 Enter；按 Enter 后验证输入框已清空，否则视为发送失败；
- 发送失败：同一消息重试 N 次（可配，默认 2），仍失败则记日志 + 标记需人工。红点标记随点开会话消失，因此"待回复"状态由 state 层维护，不依赖红点；
- 发送键假设为"Enter 发送"，启动时做一次检测，可配置；
- 本机按"半专用机器"设计，不做后台无干扰发送（前台动作协议见 §5.1）。

### 5.1 前台动作协议

感知层（捕获、红点扫描、OCR、LLM）可完全后台化，动作层（点击会话、粘贴发送）无法后台化：微信 4.x 为自绘控件，不响应合成的窗口消息点击，只能把真实鼠标事件打到屏幕坐标上。协议：

1. 记录当前前台窗口（`GetForegroundWindow`）；
2. `SetForegroundWindow` 带起微信，完成点击、粘贴、验证、回车（约 1~2 秒）；
3. 立即把之前的前台窗口还回去。

对使用者的体感：屏幕闪一下微信，一秒多就还回来。若被五道闸门拦截（不发送），则全程不抢前台、完全无感。

## 6. LLM 层设计

- **协议**：统一走 OpenAI 兼容的 chat completions（智谱 API 本身兼容）。适配层 = 一个可配 `base_url + api_key + model` 的客户端，天然覆盖智谱 GLM / DeepSeek / Kimi / 通义 / Ollama 本地模型。真正不兼容的协议（如 Anthropic 原生）后期再单独加适配器；
- 起步模型：智谱 flash 级免费模型，跑通后按需在配置里升级；
- 上下文：按联系人维护最近 **8~10 轮**滑动窗口（含自己发出的回复），避免重复寒暄；后期可加摘要压缩；
- 提示词：全局默认人设/业务说明占位符 + 每联系人可覆盖的个性化提示词；
- API key 存本地 config 文件，`.gitignore` 排除，不入库。

## 7. 模块划分

```
config.yaml      白名单（每人：启用、个性化提示词、频控参数）、LLM 配置、安全参数、总开关
main.py          编排主循环
vision/          截屏、变化检测(pHash)、红点扫描、气泡裁剪与分类、OCR、模板健康检查
controller/      点击会话、剪贴板写入、粘贴、回车、输入框验证
llm/             OpenAI 兼容客户端、提示词构建、上下文管理
safety/          高危词过滤、频控、总开关、审计日志
state/           每联系人会话历史、已处理消息指纹、待回复状态
```

处理循环为**串行单队列**：处理中的新消息下个扫描周期自然被扫到，不做并发。

## 8. 安全闸门链（全自动发送的前提）

每条回复发出前顺序过五道闸门，**任何一道不过 → 降级为"记日志 + 标记需人工"，绝不发送**：

| # | 闸门 | 规则 |
|---|---|---|
| 1 | 白名单 | 联系人模糊匹配白名单，含每联系人启用开关 |
| 2 | OCR 置信度 | 低于阈值（可配）不回。回错比不回更糟 |
| 3 | 高危词 | 来信含"退款、退货、投诉、报警、骗子、律师、12315、工商"等 → 转人工。词库在配置文件中，可自行增删 |
| 4 | 频控 | 同联系人回复间隔 ≥30 秒（随机抖动）；每联系人每日上限；全局每日上限；夜间时段（默认 23:00–08:00）只记录不发送 |
| 5 | 内容自检 | 粘贴后 OCR 输入框与预期一致才回车（见 §5） |

配套：

- **总开关**：配置文件字段 + 可选全局热键，一键停发；
- **审计日志**：SQLite，字段含时间、联系人、来信文本、回复文本、是否发送、拦截原因、模型、token 数、耗时。全自动模式的信任来自事后可查。

## 9. 健壮性设计

- **模板健康检查**：启动时及运行中周期性验证锚点模板（侧边栏图标、搜索框等）仍可匹配；失配 → 告警 + 暂停自动回复，**绝不静默失败**。针对 4.x 更新频繁的现实；
- 消息气泡分类失败（既不像文字也不像已知类型）→ 按非文字处理，只记日志；
- 白名单模糊匹配需防误伤：阈值保守，匹配日志记下"来信名 → 匹配到的白名单名"，便于审计。

## 10. 分期落地（每期有通过标准）

| 阶段 | 内容 | 通过标准 |
|---|---|---|
| M1 校准工具 | 实测 PrintWindow(PW_RENDERFULLCONTENT) 对微信 4.1 有效（黑图则启用 WGC 兜底）→ 定位微信窗口 → 红点检测，只输出日志 | 微信被其他窗口完全遮挡时，仍能稳定报告"XX 会话有新消息" |
| M2 识别链路 | 点击会话 → 裁剪气泡 → OCR 文本，**只记日志不回复** | 跑一天，人工核对 OCR 准确率达到可用水平 |
| M3 LLM 干跑 | 接入 GLM 生成回复，**只写日志不发送** | 人工审阅回复质量，提示词调到满意 |
| M4 全自动上线 | 打开发送，五道闸门 + 审计日志生效 | 头几天每日复查日志无事故 |
| M5 收尾 | 多供应商配置化、模板失效报警打磨 | — |

M3 的"干跑"不是变相草稿模式：发送开关一开即为全自动，干跑只是上线前验证 OCR 与 LLM 两个环节——这两环出错在全自动下都会直接发给客户。

## 11. 已定默认值汇总

| 项 | 默认值 |
|---|---|
| 发送键 | Enter 发送（启动时检测） |
| 夜间免扰 | 23:00 – 08:00 只记录不发送 |

| 发送失败重试 | 2 次，仍失败转人工标记 |
| 上下文窗口 | 每联系人最近 8~10 轮 |

| API key | 本地 config，.gitignore 排除 |

## 12. 主要风险与对策

| 风险 | 对策 |
|---|---|
| 微信 4.x 更新导致模板失效 | 锚点健康检查 + 告警暂停（§9） |
| 微信被最小化/关到托盘，窗口捕获拿不到内容 | 最小化 → `SW_SHOWNOACTIVATE` 自动恢复；托盘 → 靠使用习惯保持打开（§3.1） |
| LLM 回错话直接触达客户 | 五道闸门 + M3 干跑验证 + 审计日志 |
| 账号风控 | 随机延迟、每日上限、夜间免扰 |
| 发出乱码/错文本 | 粘贴后输入框闭环验证（§5） |
| OCR 认错字导致白名单漏判 | 模糊匹配 + 匹配结果入审计日志 |
| 剪贴板/焦点干扰人工使用 | 剪贴板保存恢复；项目按半专用机器定位 |
